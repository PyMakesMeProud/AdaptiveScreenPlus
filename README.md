# 自适应屏幕 · Adaptive Screen++（ExtDisplayRotator）

**把手机外接的便携屏、以及 Galaxy Z Flip / Z Fold 的外屏，变成真正能用的第二块屏。**

手机竖着拿、便携屏横着放时，镜像过去会留一圈黑边 —— 本应用在后台盯着手机的横竖状态，
一变竖就把外接屏跟着转 90°，让画面重新铺满；同时能**接管内屏分辨率**（可替代 SecondScreen），
检测到便携屏接入时弹窗询问、拔掉自动还原。在此之上还做了双屏并发、副屏桌面与伪应用、
内屏全面屏手势、外屏侧边栏，以及一组外屏小组件。

> **适用机型**：三星 Galaxy Z Flip / Z Fold 等支持「封面屏 + 内屏 + 外接屏」的机型。
> 部分功能依赖 [Shizuku](https://shizuku.rikka.app/)（免 root 的 adb 权限），
> 外屏启动器、回主界面、返回等已改为纯无障碍实现，不需要 Shizuku。

## 一、它解决什么问题

三星手机接便携屏（DeX 或屏幕镜像）时，画面方向和便携屏的物理朝向对不上，
便携屏的四边就会出现黑边。典型场景：

- 手机锁定横屏，但某个 App 自己强制竖屏 → 手机画面变成竖的
- 竖画面镜像到横置的便携屏上 → 左右两侧（或上下）出现大片黑边

本应用在后台监听**手机当前的横竖状态**，一旦变成竖屏，就通过 ADB（shell）权限
把外接屏旋转 90°，让画面重新铺满；手机回到横屏时自动还原。

**第二件事：内屏分辨率。** 便携屏显示的是手机内屏的镜像，两者宽高比不一致时，
即使方向对了也会出现黑边或拉伸。所以本应用还能在便携屏接入时，
把手机内屏改成指定的分辨率（默认 `1080×1920`），拔掉后自动还原 —— 这一块
原本是靠 **SecondScreen** 做的。

**为什么要自动"横转竖"？** 便携屏的面板基本都是横向的（1920×1080 之类），
而内屏镜像过去、外接屏再转 90° 之后是竖着看的。所以真正该写进内屏的是
**转置后的竖屏数值** 1080×1920。本应用会在写入前统一做这件事，
你直接粘 1920×1080 进去也不会出错。

> ⚠️ **不要两个应用同时管显示**。手机主屏的分辨率和旋转属于同一套显示几何，
> 被两个来源同时改写会形成竞态，症状是镜像画面整体平移、只剩约 1/4 在屏内
> （详见第五节）。要么用本应用（旋转 + 分辨率都归它管），要么用 SecondScreen。

> 为什么不能"自动检测便携屏的物理朝向"？
> HDMI / USB-C 的 EDID 里只有分辨率和刷新率，**没有任何关于屏幕被怎么摆放的信息**。
> 便携屏不会、也无法告诉手机它是横着还是竖着放的。
> 因此只能选一个判断依据 —— 本应用用的是"手机自己的横竖状态"，这也是最贴近你需求的方案。

## 二、原理

Android 从 10 开始，`wm` 命令支持**针对指定显示屏**设置旋转：

```bash
# 查看所有显示屏及其 ID
adb shell dumpsys display | grep -i "mDisplayId="

# 让外接屏忽略 App 自己申请的屏幕方向
adb shell wm fixed-to-user-rotation -d <屏幕ID> enabled

# 把外接屏锁定到指定角度（0=0°, 1=90°, 2=180°, 3=270°）
adb shell wm user-rotation -d <屏幕ID> lock 1

# 恢复系统自动
adb shell wm user-rotation -d <屏幕ID> free
```

内屏分辨率用 `wm size`：

```bash
# 给内屏加分辨率覆盖 / 清除
adb shell wm size 1080x1920
adb shell wm size reset

# 顺便改 DPI（可选）
adb shell wm density 480
adb shell wm density reset
```

> ⚠️ **`wm size` 的 `-d` 参数有坑**（真机逐条验证过，Galaxy Z Flip5 / Android 16）：
>
> | 命令 | 实际行为 |
> |---|---|
> | `wm size -d 0` | ✅ 读取 display 0 的尺寸 |
> | `wm size -d 0 1080x2160` | ❌ **`-d` 被忽略，命令退化成"读取"，写不进去** |
> | `wm size 1080x1920` | ✅ 真正写入（默认作用对象就是 display 0 = 内屏） |
> | `wm size reset` | ✅ 清除覆盖 |
>
> 注意这跟 `wm user-rotation` 不一样 —— 那一条的 `-d` 是生效的，
> 要给外接屏设旋转**必须**带。（见 `ScreenSizeUtil.java` 的注释。）

### 怎么知道该给内屏配多少分辨率

读外接屏的**面板原生分辨率**，用 `Display.Mode` 的 `physicalWidth/Height`：

```java
Display.Mode m = display.getMode();
int w = m.getPhysicalWidth();    // 面板真正的像素矩阵，例如 1920
int h = m.getPhysicalHeight();   // 例如 1080
```

**为什么不用 `Display.getRealSize()`**：它返回的是**当前逻辑**尺寸，会被
`wm size` 覆盖和旋转影响 —— 内屏已经被改过之后再读它，读到的是改过的值，越读越乱。
`Display.Mode` 才是面板自己的尺寸。

拿到之后过一道**竖屏规范化**（`ScreenSizeUtil.portrait`，保证 高 ≥ 宽）：

```
面板 1920×1080  →  规范化  →  内屏写 1080×1920
面板 1080×1920  →  规范化  →  内屏写 1080×1920（本来就是竖的，不动）
```

这一步放在 `ScreenSizeUtil.apply()` 里 —— 那是全应用**唯一真正写盘的地方**，
放这里可以保证无论从哪个入口（弹窗、按钮开关、自动套用）进来都不会把横屏值写进内屏。

普通 App 拿不到 shell 权限，所以本应用借助 **Shizuku** 把 ADB 权限"借"过来，
然后在后台把这些命令下发给系统。

### 关于"插入时弹窗询问"

Android 10 起 App 在后台启动 Activity 默认会被系统拦截。本应用用**三条腿**保证询问一定能送达：

| 顺序 | 方式 | 条件 |
|---|---|---|
| 1 | 真正的对话框（`PromptActivity`） | 已授予「显示在其他应用上层」权限时，后台启动 Activity 是官方明确的豁免项 |
| 2 | 用 shell 身份执行 `am start` 拉起同一个对话框 | shell（uid 2000）不受后台启动限制；Shizuku 派生的进程正好就是 shell 身份 |
| 3 | 高优先级**横幅通知**，带「启用 / 不用」按钮 | 永远可用，`POST_NOTIFICATIONS` 已授权即可 |

所以即使弹窗权限没给，插上便携屏时也会看到一条横幅可以直接点「启用」。
界面上有 **「授予弹窗权限」** 按钮：先尝试通过 Shizuku 执行
`appops set ... SYSTEM_ALERT_WINDOW allow`（**v1.3 已在清单里声明该权限，所以这条能生效**），
失败再跳到系统设置页。另有 **「测试弹窗」** 按钮，可以随时验证这条链路。

### 响应速度是怎么保证的（v1.5 重点修的）

**症状**：手机一转方向，便携屏要等 3 秒左右才跟着翻。真实机实测 2.59 / 3.32 秒。

**原因**：不在命令执行（`wm` 单次只要 **0.02 秒**），而在**决策环节被轮询周期整段放大**：

```
旧逻辑（错）
  用户转手机 ──► 系统改内屏 rotation
                    │
                    ├─ 要等最多 2.0 秒才有一次轮询路过，才发现方向变了  ← 延迟 ①
                    ├─ 发现了，记下"方向变化时刻"，但要求稳定 0.9 秒才动作
                    └─ 而这个检查又要等下一次轮询才能碰到              ← 延迟 ②
  合计 2 ~ 4 秒（两处延迟都被"量化"成一个完整的轮询周期）
```

**修法**（`RotationService.java`）：

| 改动 | 说明 |
|---|---|
| 显示事件驱动（`onDisplayChanged`，**只认 display 0**） | 手机内屏一变化立刻评估，延迟 ① 归零。外接屏自己的变化是我们命令的回声，忽略，不会自激 |
| 「预约一次评估」代替"等轮询" | 方向一变就 `postDelayed(eval, STABLE_MS+30)`，稳定期一结束立刻动手，延迟 ② 归零 |
| `STABLE_MS` 900 → 400 ms | 系统本身已对重力感应去抖（`getRotation()` 报出来就是稳定值），这里只是再拦一道短促来回 |
| 轮询 2000 → 1500 ms | 降级为兜底，防事件丢失 |
| 静默期可提前解除 | 原来发现命令没生效要死等满 2.5 秒才补发；现在只要"上一刀已确认落地"（当前角度＝上次的目标角度）就能走，手机来回翻转不再被无谓压住 |

**实测对比**（同一台 Galaxy Z Flip5，同一套 adb 计时协议）：

| 操作 | 修复前 | 修复后 |
|---|---|---|
| 转竖屏 | 2.59 s | **0.44 s** |
| 转横屏 | 3.32 s | **0.45 s** |
| 快速回切（1.2 s 内来回） | 被静默期压住 | **0.44 s** |

> `evalRunnable` 与 `pollRunnable` 刻意分成两个 Runnable：轮询是自续链，
> 共用同一个 Runnable 会在 Handler 上挂出两条链，`removeCallbacks` 撤不干净，
> 评估次数会莫名翻倍。

### 为什么还会"偶发只剩 1/4 屏"，以及怎么根治（v1.6 重点修的）

**症状**：接上便携屏的那一刻、或折叠机从折叠切到展开时，偶尔只显示 1/4 画面。
**注意它和内屏切横竖屏无关** —— 内屏切方向时不会犯，这两种场景都会犯。

**根因：旧逻辑只校验"角度"，不校验"几何"。**

外接屏的旋转命令是 `wm user-rotation -d <id> lock <角度>`。旧逻辑每次评估时先读
外接屏当前 `rotation`，如果已经等于目标角度，就认为"已经到位"，**跳过下发**。

但插屏 / 折叠展开会让系统**重新计算整块屏的显示几何**（尺寸、位移、裁切窗口），
而这块屏的 `rotation` 数值往往**没变**（比如仍然是 1=90°）。于是：

```
插上便携屏 / 展开  ──►  系统重算几何，只算到一半（1/4 画面）
                          │
                          └─ 应用评估：读 rotation = 1，等于目标角度 1
                                       └─ "已在位，无需动作" → 不下发命令
                                                    ↓
                              半成品几何就这么留在屏幕上 = 1/4 屏
```

内屏切横竖屏时 `rotation` 值**会**变，所以每次都会触发下发、把几何重排一遍，
反而不会犯 —— 这也解释了"为什么只有这两种场景偶发"。

**修法（`RotationService.java`）：两把新尺子**

| 新机制 | 做什么 | 解决哪一步 |
|---|---|---|
| **拓扑签名**（`topologyKey`） | 把"内屏 on/off + 内屏面板原生尺寸 + 外接屏集合"拼成一个字符串。只要它变了，就判定"发生了插拔/折叠" | 抓住"需要重排"的那个时刻 |
| **几何校验**（`geometryOk`） | 读外接屏真实 `getRealSize()`，必须等于"面板原生尺寸按目标角度转置"后的值。不等 ⇒ 判定几何是半成品 | 抓住"已经错位"的状态 |

**处置流程**：

1. 拓扑签名变化（插屏 / 折叠展开）→ 记 `pendingRepair`，等 `TOPO_SETTLE_MS`(900ms)
   让系统把那一次几何重算做完，再执行一次**完整的 `free → lock` 重排**（对每个外接屏）。
2. 每次常规评估都额外做一次 `geometryOk` 检查；一旦发现真实尺寸 ≠ 期望尺寸，
   立刻强制重排一次（保留 `MAX_GEOM_REPAIR` 次重试 + 退避，避免抖动）。
   > ⚠️ **v2.0 修正**：这一步的前提是**外接屏的角度已经落在目标上**。
   > 角度还没到位时"尺寸不符"是必然的中转状态，不该判成几何坏了 ——
   > 否则手机每转一次方向都会白做一次 `free → lock`，而 `free` 期间外接屏会跟着
   > 系统自己重算方向，看起来就是当场乱转。详见第二节 v2.0 那一节。
3. 重排一律走 `free → lock`：先 `wm user-rotation -d <id> free` 让系统放开，
   再 `wm fixed-to-user-rotation -d <id> enabled` + `lock <角度>` 重新锁定。
   这套组合会强制显示系统把几何完整重算一遍。

**真机验证**（Galaxy Z Flip5 / Android 16，用 `settings put global overlay_display_devices "1920x1080/320"` 模拟便携屏）：
> ⚠️ **v2.0 起这条老办法失效**：这台 One UI 上该虚拟屏（`overlay:1`）没有 PUBLIC 标志，
> 第三方 App 的 `getDisplays()` 看不到它，本应用自然也看不到。要验证旋转链路只能插真屏。

```
topology changed → schedule full repair
topology re-assert → full repair
wm fixed-to-user-rotation -d 24 default
wm user-rotation -d 24 free
wm fixed-to-user-rotation -d 24 enabled
wm user-rotation -d 24 lock 3
```

20 秒静置观察无几何误报，`logcat -b crash` 为 0。

### 弹窗为什么要"按窗口等比缩放"（v1.6）

横屏时手机可用高度很矮，而弹窗内容（标题 + 分辨率 + 复选框 + 两个按钮）是固定字号，
于是按钮被挤出屏幕，既看不见也点不到，还不能滚动。

修法（`PromptActivity.java`）分两层：

1. **布局层**：`ScrollView`（可滚动主体）+ **固定底部按钮栏**。按钮永远钉在底部，
   内容再多也只是中间主体滚动，绝不会把按钮顶出去。
2. **缩放层**：以"真实测得的 `body.getHeight()` vs `scroll.getHeight()`"为准做反馈循环 ——
   先按 `MAX_SCALE`(1.20) 试排，若内容超出视口，就交替"把窗口长大一点"和
   "把字号缩一点"，直到刚好放下（`settle()` 循环，40ms 一轮）。
   所以无论什么 DPI、横屏竖屏，内容都是**贴着窗口等比缩放**、完整可见。

> 弹窗走的是自定义主题 `AppPromptDialog`（`windowNoTitle=true`），
> 避免系统默认对话框标题栏白占约 50dp 高度。

### 折叠模式 / 双屏：直接驱动系统的折叠状态机（v1.7）

Android 在折叠机上把「折叠姿态」抽象成一个**设备状态机**（`DeviceStateManager`），
每个状态决定用哪块屏、几何怎么算。本应用把它做成了一个按钮，走 shell 执行：

```bash
adb shell cmd device_state print-state              # 查当前状态
adb shell cmd device_state state 3                  # 覆盖为指定状态
adb shell cmd device_state state reset              # 交还给折叠传感器
> ⚠️ **`print-state` 给的是"当前生效值"（Committed），不一定是传感器的物理姿态** ——
> 别的软件（或本应用自己的覆盖）设过 override 之后它会跟着覆盖走。想拿它判"现在该切哪边"，
> 先看版本历史 v2.8 ①（v2.8 之前就是栽在这上面）。
```

**这台 Z Flip5 实测支持的状态**（来自 `dumpsys device_state`）：

| id | 名字 | 含义 | app_accessible |
|---|---|---|---|
| 0 | CLOSED | 合上（走外屏） | 否 |
| 1 | TENT | 帐篷 | 否 |
| 2 | HALF_OPENED | 半开 / Flex | 是 |
| 3 | OPENED | 展开（走内屏） | 是 |
| 4 | **CONCURRENT_INNER_DEFAULT** | **并发：内外屏同时点亮** | 是 |

**实机逐条验证的结果**：

| 操作 | 结果 |
|---|---|
| `state 3`（展开） | 内屏 ON、外屏 OFF —— 常规展开 |
| `state 4`（并发） | **两块机身屏同时 ON**，外屏确实在渲染内容（抓到充电信息页） |
| `state reset` | 交还给折叠传感器 |

即：**不需要 root、不用改固件，一条 shell 命令即可让内外屏同时点亮**，
且完全不依赖 DeX（Z Flip5 官方本来就没有 DeX）。

> ⚠️ 状态覆盖是**持久**的，除非点「恢复自动」，否则一直生效。
> 另外 `CONCURRENT_INNER_DEFAULT` 带 `cancel_when_requester_not_on_top=true`，
> 请求方不在前台时可能被系统自行取消 —— 适合手动点一下看效果，不适合当常驻模式。

### 封面屏点亮了却一片黑：为什么，以及怎么变成真副屏（v1.8）

`state 4` 让封面屏亮了，但上面只有系统自己挂的一个空跑的 `SubHomeActivity`
（三星封面屏那套界面在「非折叠」状态下不渲染内容），看着就是黑的 ——
**屏亮着却没有能点的东西，算不上"第二块屏"**。

v1.8 的做法是往那块屏上**投一个我们自己的轻量桌面**：

```bash
# 往封面屏（displayId = 1）投副屏桌面 / 投任意应用
adb shell am start --display 1 -n com.wb.extrotator/.SecondaryHomeActivity
adb shell am start --display 1 -n <第三方应用包名>/<它的 Launcher Activity>

# 想把封面屏交还给系统桌面
adb shell am start --display 1 -a android.intent.action.MAIN -c android.intent.category.HOME
```

`--display N` 是以 shell（Shizuku）身份执行的，而 shell 持有 `START_ANY_ACTIVITY`，
所以**能启动任何组件（包括未导出的）**，第三方应用也照样投得过去。
副屏桌面上的图标被点时调的就是同一条命令 —— 内容因此落在**它自己那块屏**上，
便携屏同理（把 `1` 换成便携屏的 id）。

**踩到的坑（很隐蔽，值得记一笔）：`dm.getDisplays()` 看不到封面屏。**

并发模式下 `dumpsys display` 里封面屏（`displayId=1`）明明在、`state ON`，
但**应用进程调 `DisplayManager.getDisplays()` 只会返回内屏一块**，
封面屏整个从列表里消失；而 `dm.getDisplay(1)` 是能正常拿到的。

后果：用 `getDisplays()` 去找封面屏永远返回 null，界面把它标成"外接屏"，
「投副屏桌面」的按钮一直提示"没找到目标屏"。
**解法：不要用 `getDisplays()`，改成按 id 从 0 到 12 逐个 `getDisplay(id)` 探测**
（见 `DisplayUtil.allDisplays()`）。

> 顺带一个安全收益：`externalDisplays()`（决定要不要下发旋转命令）**仍然只用
> `getDisplays()`**，而它天然看不到封面屏 —— 所以并发模式下也不会误把机身外屏
> 当成外接屏去旋转，正好是之前用"三道闸门"想达到的效果。

> 另一处小坑：**XML 注释里不能出现连续两个连字符**。文档正文里写
> `am start --display N` 完全合法（属性值、文本框里都行），
> 但写进 `AndroidManifest.xml` 的注释里会让构建直接报
> `ManifestMerger2$MergeFailureException: Error parsing AndroidManifest.xml`，
> 而且不告诉你在第几行。

### 桌面小组件：为什么用「透明 Activity」而不是广播或服务（v1.9；v2.2 合并为一个）

> **v2.2 起只有一个小组件了 —— 「双屏快捷面板」**（`PanelWidgetProvider`）。
> 原来那两个（`DualWidgetProvider`「一体双屏」 / `FoldWidgetProvider`「折叠 / 展开」）
> 已删掉，源码归档在 `process/archived-v22/`。合并原因：两个组件各自要占格子、
> 各自要写一份布局与文案，而用户要的就是"两个按钮并排"这一件事。
> 新的面板是 **2×1 的最小尺寸**，左边「折叠/展开切换」、右边「双屏模式」，点一下就有 Toast 反馈。

小组件只做一件事：被点时弹一条 Toast 并执行命令。真正干活的地方是一个
**透明的、无历史的 Activity**（`WidgetActionActivity`，主题 `Theme.Translucent.NoTitleBar`）。

为什么不用更"正统"的 `PendingIntent.getBroadcast` + 前台服务：

1. 小组件的 PendingIntent 是**用户主动触发**的，系统把它算作前台交互，
   不受「后台启动 Activity 被拦」那条限制 —— 这条豁免本来就是为小组件准备的；
2. 要用 Shizuku 就必须在应用进程里拿到 binder，Activity 天然满足；
3. 广播接收器在后台弹 Toast 不稳妥，而这里**必须有反馈**（"正在切到并发双屏…"这类），
   否则用户点了没反应会以为坏了。

界面上一闪而过的窗口是透明的，看不出任何东西，只有一条 Toast。

两个实现细节：

- **多个入口共用一段代码**。切并发、等外屏就绪、投桌面这一串（含"必须等约 2 秒"
  的时序）全部收在 `DualScreen.oneKeyDual()`；应用界面的「启动双屏模式」和
  小组件上的「双屏模式」按钮调的是同一个方法。**这类时序写在两处，迟早有一处会少等一秒
  而变成"点了没反应"。**
- **v2.2 起面板刻意做成"纯静态"**：不显示任何当前状态，布局直接写在
  `res/layout/widget_panel.xml` 里，`PanelWidgetProvider` 只设两个
  `setOnClickPendingIntent`，**不重写 `onReceive()`、不 `goAsync()`、不读 Shizuku**。
  好处是省掉一次 shell 往返（点下去本来就有 Toast 反馈），接口也没有失败的机会。
  （v1.9 那个会显示状态的折叠小组件，曾靠 `onReceive()` 拦 `ACTION_APPWIDGET_UPDATE`
  → `goAsync()` → 后台线程读状态 → `PendingResult.finish()` 实现，那套做法在
  `process/archived-v22/FoldWidgetProvider.java` 里可以捡回来。）
- **两个按钮都用 TextView + 圆角 drawable**（`widget_btn_fold.xml` / `widget_btn_dual.xml`），
  **不用 `<Button>`** —— 各家桌面会给 Button 盖自己的主题色，盖完就未必看得清了。
- 按钮文字 `maxLines="2"` 且**不设 `ellipsize`**，文案本身手工折行
  （`折叠/展开\n切换`）—— 2×1 的最小宽度下一行放不下 5 个汉字，
  会自动变成「折叠/展开…」，折行比省略号好看。

> **想放到封面屏（外屏）上**：普通"添加到主屏"只会进内屏 —— **封面屏的小组件是单独一套**，
> 要进「**设置 → 外屏 → 小组件**」里添加（有些系统版本这一项写作「封面屏幕 → 小组件」，
> 三星把这两边的组件列表分开了）。
> ⚠️ 光靠 `widgetCategory` 标志位是**进不了**这个列表的 —— 还得在 receiver 上挂一条三星
> 私有的 `com.samsung.android.appwidget.provider` meta-data，指向
> `<samsung-appwidget-provider display="sub_screen"/>`（v2.5 才找到的根因，见第六节 v2.5）。
> 面板的 `minWidth/minHeight` 已经压到 `110×52 dp`，就是为了能塞进封面屏那
> 748×720 px（约 352×339 dp）的逻辑空间。

> 小组件布局只能用 RemoteViews 支持的控件（这里是 LinearLayout + TextView），
> 而且**深色卡片底是刻意的** —— 桌面壁纸深浅不可控，白卡片配白字一旦遇上浅色壁纸
> 就什么都看不见了。

### 界面为什么要做减法：说明收进「ⓘ」、更新日志单独一页（v2.3）

**问题**：到 v2.2 为止，每个开关 / 按钮下面都挂着一段 `alpha≈0.62` 的灰色说明，
标签里还带括号注记（「跟随手机方向（推荐）」「一键启动双屏（并发点亮 + 外屏副屏桌面）」）。
4 个选项卡十几个控件铺下来，**一屏根本看不完**，说明写了也白写。

**做法**：正文只留操作名，解释一律按需展开。

| 改动 | 说明 |
|---|---|
| 新增「ⓘ」详情图标 | 布局里 id 以 `i` 开头（如 `iSwLockPhone`），由 `MainActivity.bindInfo()` 统一挂点击 → `AlertDialog` 显示 `strings.xml` 里的 `info_*` 正文 |
| 删除全部常驻说明段 | 原来 11 段 `alpha="0.62"` 的灰色说明全部移除，内容原样搬进 `info_*` |
| 括号注记收进 ⓘ | 标签只留操作名（`跟随手机方向`、`恢复自动`、`自适应旋转`…），括号里的解释进了对应 ⓘ |
| `ⓘ` 是画出来的 | 不用 `ⓘ`(U+24D8) 字符 —— 该字符在部分中文字体里缺失会变成方框；改成实心圆 + 白色小写 `i`（`drawable/info_badge.xml`），外面套 6dp `inset`，**看得见的圆 22dp、点击热区 34dp**（22dp 太小容易点空） |
| 新增「版本与更新」页 | `ChangelogActivity` + `activity_changelog.xml`，从标题旁的胶囊进入 |

**版本入口的位置**：放在标题「自适应屏幕」右边，做成一个浅蓝胶囊
「**v2.3 · 更新说明**」。没放进选项卡，是因为主界面已经有 4 个选项卡，
再挤一个进去每个都快没宽度了；更新日志也属于"偶尔翻一次"的内容，不该和日常操作抢位置。

**两个实现细节**：

- **版本号是读出来的，不是写死的**。`MainActivity.bindVersionEntry()` 和
  `ChangelogActivity` 都用 `PackageManager.getPackageInfo()` 拿 `versionName` /
  `versionCode` —— 改 `build.gradle` 之后界面自动跟着变，
  不会出现"界面写着 2.2、装的其实是 2.3"这种对不上的情况。
  日志正文里那一条 v2.3 只负责写"改了什么"。
- **更新日志在代码里，不在布局里**。13 个版本 × 每版 2 行，写成静态 XML 要多几百行
  几乎重复的标签，以后加一条还得同时改布局。改成 `ChangelogActivity.LOG` 这个
  `String[][]`（`{版本, 日期, 条目…}`，**倒序**），由 `renderLog()` 动态铺出来；
  版本号与当前版本一致的那条会自动挂一个「当前」胶囊。

### 「内屏 + 便携屏」双屏（不用 DeX）怎么实现

你的原话是：*让手机屏幕和镜像屏幕实现双屏显示，最好都能操作，像 DeX 一样，
但不要用 DeX*。Z Flip5 官方**没有** DeX（你说的"dex 是卡出来的"正是指这个），
所以正路是 AOSP 自带的**「强制桌面模式」**：

```bash
adb shell settings put global force_desktop_mode_on_external_displays 1
adb shell settings put global enable_freeform_support 1
adb shell settings put global enable_non_resizable_multi_window 1
# 需要重启才完全生效；撤销就把上面三条 delete 掉
```

打开后，接上便携屏时它**不再镜像手机**，而是变成一块独立桌面：自由窗口
（可拖动/缩放）+ 应用抽屉，鼠标操作这块屏；手机内屏照常使用 —— 两块屏各跑各的，
这才是真正的"双屏显示"。

- 三星 Flip 系列（Flip 5/6）实测可用；有 Flip 6 用户反馈"比镜像体验好得多"。
- 局限：没有任务栏/系统状态栏，窗口管理粗糙，很多 App 只是被拉伸的手机界面。
- 本机现状：`enable_freeform_support` 已经是 `1`，只差 `force_desktop_mode…` 这一条。

**所以对"鼠标操作镜像屏、外屏纯触控"的诉求**：走桌面模式后，鼠标天然归外接屏
（它就是那块桌面），触控留给机身屏 —— 正好是你要的分工。

### 「同时显示」的三个层次（结论）

| 目标 | 可行性 | 做法 |
|---|---|---|
| 内屏 + 外屏（两块机身屏）同时点亮 | ✅ 本机实测可行 | `cmd device_state state 4` |
| 内屏 + 便携屏各自独立显示（双屏 ≠ 镜像） | ✅ 可行 | AOSP 强制桌面模式（需重启，非 DeX） |
| 内屏 + 外屏 + 便携屏**三块同时** | ⚠️ 未验证 | 理论上叠加即可，但 SoC 同时驱动三块屏的带宽/发热未知，需真实硬件实测 |

> 出厂固件下「内屏和外屏同时点亮」，XDA 上 Galaxy Fold 用户是靠**刷改过的
> vendor/GSI** 才做到的，而且外屏触控还会失效。本机发现的
> `CONCURRENT_INNER_DEFAULT` 说明三星固件里本来就留了这个能力，不必刷机。

应用结构：

### 为什么"折叠时外接屏会被当场转 270°"：方向判断的输入源错了（v2.0 根治）

**现象**：接 HDMI 显示器，插上是正常的；一点「应用」整个外接屏当场转到 270°（画面侧躺），
明明手机是横屏状态。多切几次有时又正常。

**根因**：`isPhonePortrait()` 的输入源取的是 **`Display.DEFAULT_DISPLAY`（display 0，内屏）**。
而折叠机合上以后 **内屏是灭的（`state=OFF`）**，一块灭着的屏它的 `getRotation()`
**停在旧值**（这台 Z Flip5 实测恒为 0），**根本不跟着手机实际朝向走**：

```
# 手机合上、用户手持横屏、设置里 user_rotation=1（横）时的实测：
dumpsys display
  Display 0:  mBaseDisplayInfo=... rotation 0, state OFF     ← 内屏灭，rotation 恒 0
  Display 1:  mOverrideDisplayInfo=... rotation 2, state ON  ← 真正在用的是封面屏
              "内置屏幕", 748 x 720, installOrientation ROTATION_90
settings get system user_rotation   →  1        ← 用户/系统认为是横屏
settings get system accelerometer_rotation → 0
```

于是应用永远读到 `rotation == 0` ⇒ 判定"手机竖屏" ⇒ 套用设置里的
`portrait_angle`（这位用户因为便携屏摆放方向，**把竖屏角度配成了 270°**）
⇒ 对外接屏下发 `wm user-rotation -d 32 lock 3` ⇒ **横屏状态照样转 270°**。

**logcat 佐证**（事发当天 10:55–10:56 的真实记录，外接屏 id=32）：

```
10:55:37.166 phone orientation -> portrait
10:55:38.223 ShellRunner: wm user-rotation -d 32 lock 3      ← 竖屏 → 270°
10:55:47.870 phone orientation -> landscape
10:55:56.9xx ShellRunner: wm user-rotation -d 32 lock 0      ← 横屏 → 0°
```

而"多切几次有时正常"的原因也很清楚：**展开手机（内屏点亮）时** display 0 的 rotation
才开始跟随真实朝向 ⇒ 判断恢复正确。**只有内屏灭着的场景（合盖 / 息屏 / 只用外屏）才犯。**

**修法（三条，缺一不可）**：

| # | 改动 | 作用 |
|---|---|---|
| 1 | 新增 `DisplayUtil.activePhoneDisplay(dm)`：默认屏亮着就用它，**默认屏灭着就在所有内置屏里找真正亮着的那块**（合盖时是封面屏） | 方向判断的输入源不再是一块灭屏 |
| 2 | `isPhonePortrait()` 改为**先看面板原生宽高比**（`nativeSize`，即 `Display.Mode` 的物理像素），再决定 90/270 代表哪一边 | 封面屏（748×720，天生横的）的横竖映射是**反的**，旧写法对它永远给出反答案 |
| 3 | 新增 `lastPhonePortraitValid`：**一次有效读数都没读到过就什么都不做**（屏幕全灭 / 刚开机），有历史读数则沿用 | 宁可维持现状，也不凭一个凭空的"竖屏"把外接屏转飞 |

验证方式（真机实测输出）：

```
D/RotationService: phone orientation -> landscape (by 封面屏（外屏）)   ← 现在会带上依据哪块屏
```

界面「实时状态」也会直接写出依据：`手机方向：横屏（依据 封面屏（外屏） rotation=2）`。

**踩坑提醒**：`settings put global overlay_display_devices "1920x1080/320"` 这条老办法
（v1.6 用它模拟过便携屏）**现在不能用了** —— 这台 One UI 上它创建的虚拟屏
（`uniqueId=overlay:1`，displayId 34）虽然 `dumpsys display` 里看得见，
但**没有 PUBLIC 标志，第三方 App 的 `getDisplays()` 拿不到它**
（`Display.hasAccess(uid)` 为 false），所以本应用看不到，也就无从用它验证旋转逻辑。
要端到端验证这条链路，只能用**真的插一块外接屏**。

### 开启并发（双屏）后外接屏被锁死在 270°：内屏的 rotation 会被系统复位（v2.2 根治）

**现象**：外接屏接好、方向本来是正常的；一点「打开双屏模式」（或小组件上的「双屏模式」），
**外接屏就锁在 270°**（画面侧躺），怎么转手机都不回来。

**根因**：这是 v2.0 修掉的那个坑的**近亲**，但触发路径不同。

内屏（display 0）的 `getRotation()` **完全跟随系统旋转策略 `user_rotation`**（实测
`user_rotation` 0/1/2/3 与内屏 rotation 一一对应）。可切并发模式（
`cmd device_state state 4`）时，内屏会经历一次 **OFF → ON**：回来后
**`rotation` 被系统复位成 0（竖屏）**，而 `user_rotation` **仍然是 1（横屏）**。

```
settings get system user_rotation          → 1        ← 系统认为是横屏
settings get system accelerometer_rotation → 0

# 切入并发后：
dumpsys display
  Display 0:  rotation 0   state ON    ← 刚被点亮的内屏，rotation 被复位成 0！
```

于是应用只读屏上数值 ⇒ 判定"手机竖屏" ⇒ 套用 `portrait_angle`（这位用户配的 270°）
⇒ 对外接屏下发 `wm user-rotation -d <id> lock 3` ⇒ **外接屏被锁在 270°**。

**修法**：方向判断增加**第二数据源交叉校验** —— 不去问"屏上写着多少度"，
而是去问"**系统策略认为手机该是横还是竖**"：

| 改动 | 说明 |
|---|---|
| 新增 `DisplayUtil.policyRotation(cr)` | 自动旋转关着（`ACCELEROMETER_ROTATION == 0`）时返回 `Settings.System.USER_ROTATION`，否则返回 `-1`（无意见，交给屏上读数） |
| 新增 `DisplayUtil.isPortraitAt(d, rotation)` | 把"某块屏在某个 rotation 下算不算竖屏"抽成显式函数（内部仍按面板原生宽高比判断），供策略值复用 |
| `RotationService` 里对**默认屏**加校验 | 策略值有效且与屏上读数矛盾时，**采信策略值**；只在矛盾刚出现时打一条警告（`lastMismatchKey` 去重），不刷屏 |

```
if (phone != null && phone.getDisplayId() == Display.DEFAULT_DISPLAY) {
    int policy = DisplayUtil.policyRotation(getContentResolver());
    if (policy >= 0) {
        boolean byPolicy = DisplayUtil.isPortraitAt(phone, policy);
        if (byPolicy != p) {
            Log.w(TAG, "手机方向：屏上读数与系统策略不一致，采用策略（user_rotation="
                    + policy + " → " + (byPolicy ? "竖屏" : "横屏") + "）");
            p = byPolicy;
        }
    }
}
```

**只对默认屏做这件事** —— 封面屏（外屏）是独立的物理朝向，**不受 `user_rotation` 驱动**，
对它套策略值反而是错的。

真机验证：4 轮"展开→并发→收起"切换，每轮都命中
`采用策略（user_rotation=1 → 横屏）`，外接屏不再被误锁 270°；
日志去重生效后每轮只 0~1 条，不再每秒刷一条。

### 每次转手机都会多一次"无意义重排"：几何校验跑得太早（v2.0 修掉）

v1.6 加的几何校验（`geometryOk`）判据没错，但**执行时机**错了：它在
"算出目标角度之后、下发 lock 之前"就无条件跑。而手机刚转方向时，外接屏的角度
**还是上一轮的旧值**，此时"真实尺寸 ≠ 新目标应有的尺寸"是**必然的中转状态**，
不是几何坏了。于是：

```
10:55:02.081 phone orientation -> landscape
10:55:02.512 geometry mismatch id=32 expected 1920x1080 actual 1080x1920 (target 0°)
10:55:02.513 geometry mismatch → full repair #1          ← 每转一次都误报一次
10:55:02.567 wm fixed-to-user-rotation -d 32 default     ← 于是多做一次 free → lock
10:55:02.619 wm user-rotation -d 32 free                 ← free 期间外接屏跟随系统自己重算
10:55:03.146 wm user-rotation -d 32 lock 0
```

`free` 那一瞬间外接屏会跟着系统/应用自己重算方向，屏幕就会**当场乱转一下**
（这正是"当场被转了 270°"的观感来源之一）。

**修法**：几何校验加一个前置条件 —— **只有外接屏的角度已经落在目标上时才校验**。
角度没到位时该走下面的 `lock` 分支把角度搬过去；万一搬完几何还是坏的，
下一次评估（角度已到位）仍然会抓到，**能力一点没少，误报全消**。

```
boolean angleAtTarget = true;
for (Display d : ext) { if (d.getRotation() != target) { angleAtTarget = false; break; } }
if (angleAtTarget && !geomCheckUnreliable && !geometryOk(ext, target)) { ... }
```

### 关掉「自适应旋转」后手机还是被钉在横屏（v2.0 修掉）

「方向同步」开启时会把手机自己的自动旋转关掉（`accelerometer_rotation 0` +
`user_rotation 1`，即「锁手机方向」这个功能）。还原它的代码**只写在 `ACTION_STOP` 里**，
而界面关开关时的分支是：

```java
} else if (prefs.shouldKeepRunning()) {   // 「内屏分辨率接管」还开着 → 服务必须继续常驻
    RotationService.start(this);          // 于是永远走不到 ACTION_STOP
}
```

结果：只要分辨率接管开着，关掉方向同步之后 **手机就一直被钉在横屏、自动旋转一直是关的**，
而应用这边还在按"手机横屏"算角度 —— 用户看着就是"怎么摆都不转，屏幕却在乱转"。

**修法**：新增 `ACTION_UNLOCK_PHONE` + `RotationService.restorePhoneRotation(ctx)`，
关闭开关时**无论服务是否继续常驻都先把 `accelerometer_rotation` 还回 1**；
如果顺手把服务拉起来只为发这条命令，发完自己 `stopSelf()`，不留空的前台服务。

## 三、安装与使用

### 1. 安装 Shizuku 并启动服务

1. 从应用商店 / 官网安装 **Shizuku**（包名 `moe.shizuku.privileged.api`）
2. 启动 Shizuku 服务，两种方式任选：
   - **走无线调试（不用电脑）**：开发者选项里打开「无线调试」，在 Shizuku 里选择
     通过无线调试启动，按提示配对即可（Android 11+）
   - **走电脑**：USB 连电脑，执行
     `adb shell sh /sdcard/Android/data/moe.shizuku.privileged.api/start.sh`

### 2. 安装本应用

```
result/ExtDisplayRotator-v1.5-debug.apk
```

传到手机点击安装即可（需要允许"安装未知来源应用"）。

> 如果你之前用 **SecondScreen** 在提供内屏分辨率，装好本应用后请把它关掉
> （或至少停用它的自动配置），别让两个应用同时改显示参数。

### 3. 授权 + 开启

1. 打开「外接屏方向管家」，点 **授权 / 重新检测**，在弹窗里允许
2. 打开 **启用自动方向同步** 开关
3. 允许通知权限（前台服务需要常驻通知）

此时通知栏会出现一条常驻通知，显示当前状态和快捷按钮。

### 4. 接管内屏分辨率（可选，用来替代 SecondScreen）

1. 点 **「授予弹窗权限」** —— 有它才能在插入便携屏时弹出对话框
   （没给也能用，只是退化成通知横幅）
2. 点一下那个大按钮 **「内屏分辨率接管：已关闭 → 点击开启」**，它会变成绿底
   并立刻把内屏切成当前分辨率；再点一下就是关闭 + 还原原生
3. 分辨率保持默认的 `1080×1920` 即可。**不用自己去查便携屏是多少像素** ——
   保持 **「分辨率自动加载」** 开着，插上屏时它会自动算好
   （便携屏是 1920×1080 就自动用 1080×1920）；也可以随时点
   **「读取便携屏分辨率并填入」** 手动填一次
4. 可以点 **「测试弹窗」** 先看一眼询问长什么样
5. 以后每次插上便携屏 → 弹出询问 → 点「启用」→ 内屏切到该分辨率；
   拔掉后自动还原原生分辨率

> **横屏数值会被自动转成竖屏。** 输入框下面有一行实时提示
> 「横屏分辨率会自动转成竖屏：1920×1080 → 1080×1920／当前将写入内屏：1080×1920」，
> 照着它确认就行。

> **什么时候用 DPI？** 改了分辨率但觉得字/控件大小不对时再动它。
> 留空或填 `0` = 不改。改了之后点「还原原生」会连 DPI 一起还原。

### 5. 校准方向（第一次必做）

不同的便携屏，"转 90°"和"转 270°"铺满的效果方向是相反的。
用界面下方的 **手动校准** 按钮逐个试：

- 点 `90°` → 看便携屏是否铺满
- 若方向反了，点 `270°` → 应是正确方向

然后把正确角度填到上方 **"手机竖屏时，外接屏锁到"** 的下拉框里。

### 6. 双屏（可选）

v1.9 起这块**被刻意简化成"一个按钮 + 一个开关"**：
两条入口都在「双屏」页，都需要 Shizuku 授权。

| 按钮 | 做什么 | 什么时候用 |
|---|---|---|
| **启动双屏模式**（绿色大按钮） | 一步到位：切 `state 4`（内外屏并发）→ 等系统把外屏那块 Display 建好 → 把副屏桌面投到外屏 | 想让手机和外屏同时用，就用它 |
| **快捷小组件** | 调系统的"添加到主屏幕"确认框，把小组件钉到桌面 | 想以后从桌面点一下就进双屏 |
| **鼠标检测**（与右边开关并排） | 读 `dumpsys input` 的鼠标路由并翻译成"手机内屏 / 封面屏 / 外接屏" | 接了鼠标、想确认它归哪块屏 |
| **免 DeX 桌面模式**（与左边按钮并排） | 开关 `force_desktop_mode_on_external_displays`（绿=已开，需重启生效） | 想让外接屏变成独立桌面、鼠标归它 |

> 最后两个按钮 **v2.4 起并排成一行**：一个简单功能原来占满一整行太浪费。
> 注意它俩管的是**外接屏（便携屏）**，跟「启动双屏模式」点的**封面屏**不是同一块屏，
> 两个功能不重复 —— 详见第六节 v2.4 的说明。

**外屏点亮之后就是一张能操作的副屏桌面**（时钟 / 电量 / 应用图标网格，底部「刷新 / 系统桌面 / 退出」）。
**在副屏桌面上点图标，就在那块屏上打开应用** —— 所以不需要再在手机这边搞一个"选应用"的界面，
这也是 v1.9 把之前的「封面屏选应用…」等按钮删掉的原因。

> 「内屏管理」页保留**折叠/展开模式切换**与**恢复自动**两个按钮，
> 但 v1.8 那个「内外屏双屏并发」按钮已经删掉 —— 它和「启动双屏模式」是同一件事，
> 留在两个地方只会让人不知道该点哪个。

**桌面小组件（v1.9）**：长按桌面 → 小组件 → 自适应屏幕，可以看到两个：

| 小组件（**只有一个**） | 点一下做什么 |
|---|---|
| **双屏快捷面板**（2×1，两个按钮） | 左「折叠/展开切换」= 覆盖折叠状态机：折叠 ↔ 展开；右「双屏模式」= 等同于上面的「启动双屏模式」。点完弹一条 Toast 反馈 |

> **想把它放到封面屏（外屏）上**：普通"添加到主屏"只进内屏。封面屏的小组件是
> **单独一套**，要到「**设置 → 外屏 → 小组件**」里添加（有的系统版本写作
> 「封面屏幕 → 小组件」，指的都是同一处）。

**想把"手机 + 便携屏"变成真正的双屏（像 DeX，但不用 DeX）**：见第二节
「内屏 + 便携屏」双屏怎么实现 —— 打开系统自带的**强制桌面模式**，
便携屏就变成一块独立桌面（鼠标操作），手机内屏照常用。
这个开关现在已经做进 App（「双屏」页的**免 DeX 桌面模式**）。

## 四、设置项说明

v1.7 起界面分成多个选项卡（会记住你上次停在哪一页）。屏幕上的实际顺序是
**① 授权与状态 → ② 自动旋转 → ③ 内屏管理 → ④ 双屏**。下面按功能分组叙述，每节标注了它属于哪一号选项卡。

**选项卡 ②「自动旋转」**

| 设置 | 含义 |
|---|---|
| 启用自动方向同步 | 总开关：开＝监听手机方向并把它同步给外接屏。**关掉它并不影响下面那个「关闭手机自动旋转，锁定横向」—— 两者 v2.5 起各自独立** |
| 关闭手机自动旋转，锁定横向 | 等价于在下拉快捷开关里关掉「自动旋转」并固定横向。做法只是两条 `settings` 命令：`accelerometer_rotation 0` + `user_rotation 1`，**不会强制任何应用横屏**。**v2.5 起独立生效**（不必先开上面的方向同步；开着它服务也会常驻）；关掉开关时自动还原成「自动旋转」 |
| 同步模式 · 跟随手机方向 | 手机竖屏 → 用"竖屏角度"；手机横屏 → 用"横屏角度"（默认 0°） |
| 同步模式 · 固定角度 | 不管手机什么方向，永远锁同一个角度 |
| 手机竖屏时锁到 | 建议 90° 或 270°，按校准结果选 |
| 手机横屏时锁到 | 一般保持 0° |
| 强制忽略应用申请的方向 | 对应 `wm fixed-to-user-rotation enabled`，**建议开启**，否则某些 App 会把方向改回去。每块屏只会下发一次（这个设置是持久的） |
| 修复画面（**v2.7 起搬到页面顶端那排按钮里**） | 对外接屏做一次「先 free 再 lock」的完整重排，用于镜像画面整体偏移时救急 |
| **保存参数设置**（**页面最顶端**；v2.5 新增 / v2.6 移到顶部 / v2.7 压成 3 行） | 首行是一条摘要：`display N · 面板 W×H · 设置分辨率 1080×1920（已保存）` —— 末尾那个括号说的就是**这个分辨率存没存**。下面是一张**一行两项**的对照表（共 3 行，每项都有 `已保存` / `当前` 两列）：跟随手机时是 方向同步 · 同步模式 · 自动旋转 · 竖屏方向 · 横屏方向 · DPI；切到固定角度则把后两项换成 固定角度 · 忽略方向（子选项只在它生效时露脸）。方向不写 `270°` 而是直接说 **`竖屏锁定` / `横屏锁定`**（`0°/180°` 是横着看，`90°/270°` 是竖着看）。⚠️ 但「**自动旋转**」那一格是**手机**自己的方向（三态：`开` / `横向锁定` / `竖向锁定`），跟这两项的**外接屏**语义相反，别串味（v2.8 ①③）。**两列不一样，就是"改了但还没存"**。表下那排小按钮：「**保存设置**」把当前整套（13 项，含分辨率与 DPI）按**屏幕身份**存到这块屏名下、「**清除记录**」删掉档案、「**修复画面**」救急。匹配用 `Display.getUniqueId()`（拿不到就退回 屏名 + 面板原生分辨率），**不认 displayId** —— 同一块屏换个口插进来照样认得。下次它接入时，服务在**接屏那一刻**自动套用（早于"自动调分辨率"，否则这一轮用的还是旧参数），并且**不再弹询问框**。没接外接屏时整张表收起、按钮置灰 |

**选项卡 ③「内屏管理」**

| 设置 | 含义 |
|---|---|
| **内屏状态**（**页面最上方**） | 等宽字状态块，样式与「实时状态」「副屏状态」一致：填写的分辨率（含"横向"提示）/ 实际写入内屏的尺寸 / DPI / 内屏当前是否被覆盖（原生 · 由本应用覆盖 · 被其它应用覆盖）/ 弹窗权限。**v2.4 起从「接管时机」的末尾移到页面最上面** —— 它其实是整页的状态出口，和「接管时机」那节的开关没有关系 |

## 五、常见问题

**Q：我已经在 Shizuku 里给本应用授权了，但打开应用还是显示"未检测到 / 未就绪"** ⭐

这是 **v1.0 的一个真实 bug，v1.1 已修复**。原因在 `AndroidManifest.xml`：

```xml
<!-- ❌ 错误：shell 不持有这个权限，Shizuku 服务无法把 binder 递交给本应用 -->
android:permission="moe.shizuku.manager.permission.API_V23"

<!-- ✅ 正确：shell（uid 2000）实际持有的是这个 -->
android:permission="android.permission.INTERACT_ACROSS_USERS_FULL"
```

`ShizukuProvider` 是 Shizuku 服务（以 **shell uid=2000** 运行）把 binder 递交给你的应用的通道。
系统在打开这个 provider 时会校验**调用方（即 Shizuku 服务）**是否持有声明的权限：

- `moe.shizuku.manager.permission.API_V23` → 这是发给**客户端应用**的权限，**shell 并不持有**
  → 系统直接拒绝，报 `Permission Denial: opening provider ... requires ...API_V23`
  → 应用永远收不到 binder，界面就一直显示"未检测到 Shizuku"
- `android.permission.INTERACT_ACROSS_USERS_FULL` → **shell 持有**（`granted=true`），检查通过

> ⚠️ 这个错误在 **root 模式**下不会暴露，因为 uid=0 通过一切权限检查。
> 所以很多教程照抄了 API_V23 也能"跑通" —— 一旦改用 ADB / 无线调试启动就必然失败。
> 判定依据：看 logcat 里有没有 `failed send binder to user app`。

排查命令：

```bash
# 1. 看 Shizuku 服务是否在跑（应为 shell 身份）
adb shell ps -A | grep shizuku

# 2. 看应用有没有收到 binder（出现这行就说明通了）
adb logcat | grep ShizukuProvider     # 期望看到 "binder received"

# 3. 看有没有被拒（有这行就是 provider 权限配错了）
adb logcat | grep "failed send binder"
```

**Q：通知栏看不到那条常驻通知（也没有"转 90°/还原自动"按钮）**

Android 13 起通知是运行时权限。如果安装时拒绝了通知权限，前台服务的通知会被系统隐藏，
通知栏的快捷按钮也就用不了。到「设置 → 应用 → 自适应屏幕 → 通知」里打开即可。
（应用本身仍会在后台正常工作，只是没有可见通知。）

**Q：通知栏显示"等待 Shizuku 授权"**
Shizuku 服务没在运行，或本应用没被授权。打开 Shizuku 启动服务，再回本应用点授权。

**Q：手机重启后失效**
Shizuku 本身在重启后需要重新启动服务，这是 Shizuku 的机制，不是本应用的问题。
重新启动 Shizuku 后即可恢复。

**Q：转了 90° 反而变得更奇怪**
说明你便携屏的摆放方向和 90° 相反，改用 270°。

**Q：某些 App 里旋转会被改回去**
确认 **"强制忽略应用自己申请的方向"** 已勾选。本应用每 2 秒会检测一次漂移并重新下发。

**Q：手机横竖屏切换时，便携屏画面整体错位，只剩大约 1/4 留在屏幕里** ⭐⭐

这是 **v1.2 重点排查并加固** 的问题。它的本质是「显示几何被多个东西同时改写」：

手机镜像到便携屏时，**画面内容 = 手机主屏的镜像**。手机主屏的「分辨率 / 旋转」这两项几何信息，
一旦被两个不同的来源在很短时间内分别改写，显示系统就可能算出前后不一致的布局 ——
表现就是画面整体平移半个屏，只剩四分之一露在屏里。因为是竞态，所以「有概率」。

**实测证据（来自这台 Z Flip5，通过 adb 抓取）**：

```bash
# 1) 手机主屏上存在一个别人留下的分辨率覆盖（本应用从不设置 wm size）
adb shell wm size
#   Physical size: 1080x2640
#   Override size: 1080x1920     ← 被覆盖了

# 2) dumpsys window 里留有显示尺寸/DPI 被改写的完整历史
adb shell dumpsys window | grep -i DisplaySizeDensityChangedReason
#   ProcessName=com.farmerbb.secondscreen.free, displayId=0,
#   caller=WindowManagerService.setForcedDisplaySize /
#          setForcedDisplayDensityForUser / clearForcedDisplaySize
```

即：设备上装着并**正在运行**另一个同样在改显示几何的应用（例如 **SecondScreen**），
它和本应用一起写同一套显示参数 → 竞态 → 错位。

**处理顺序（按优先级）**：

1. **不要让两个应用同时管显示**。用本应用时，把 SecondScreen 之类的
   「镜像分辨率 / 自动改分辨率」应用停掉或停用它的自动配置。
2. **清掉手机内屏上残留的分辨率覆盖**：点应用里的 **「还原原生」**
   （等价于 `adb shell wm size reset`）。
   应用首页会把这项状态直接显示出来：正常会写「（原生，无覆盖）」，
   被覆盖时会给出覆盖前后的尺寸，并标明是**本应用**还是**别的应用**设的。
3. 已经错位了想马上救回来：点 **「修复画面」** 或通知里的「修复画面」按钮，
   它会对便携屏做一次 `free → lock` 的完整重排，强制显示系统重算布局。

**v1.2 在本应用侧做的加固**（降低触发概率，这几点都是真实存在的缺陷）：

| 加固项 | 之前的行为 | 现在 |
|---|---|---|
| shell 执行线程 | 在主线程里 `waitFor()`，会卡住服务主循环，导致显示回调排队后集中爆发 | 全部丢进单线程队列异步执行 |
| 触发源 | 监听 `onDisplayChanged` —— 而它是自己下发命令的"回声"，等于自己触发自己 | 只监听显示屏**增删**，不监听变化 |
| 方向去抖 | 手机方向一有变化立即下发 | 方向需稳定 900 ms 才动作，拒绝重力感应抖动 |
| 命令节流 | 冷却 1.2 s，事务没提交完就可能补刀 | 每次下发后有 2.5 s 静默期，期间绝不发第二条 |
| 重试 | 每 2 秒无条件重发 | 静默期后校验，不符才补发；同一角度最多 2 次，之后转 15 秒慢速重排 |
| `fixed-to-user-rotation` | 每次旋转都重发（多一次显示重配置） | 每块屏只发一次 |
| 误旋机身屏 | 折叠机外屏（Z Flip）可能被当成外接屏而被旋转 | 见下一条 |

**Q：接上便携屏、或折叠机展开时，偶尔只显示 1/4 画面** ⭐⭐

这是 **v1.6 根治**的另一个 1/4 屏来源，和上面那条（两个应用抢着改几何）**不是同一回事**：

- **触发场景**：刚接上便携屏的那一刻，或从折叠切到展开的那一刻。
  **内屏切横竖屏时不会犯** —— 这正是它的特征。
- **原因**：插屏 / 展开会让系统**重算显示几何**，但外接屏的 `rotation` 角度值往往不变。
  旧逻辑只看角度，发现"角度已对"就跳过下发，于是系统那套算了一半的几何留在屏上。
- **v1.6 怎么修的**：除了角度，再校验两件事 ——
  **拓扑签名**（内屏 on/off + 内屏面板尺寸 + 外接屏集合）一旦变化就触发一次完整重排；
  **几何校验**（外接屏真实尺寸是否等于面板原尺寸按目标角度转置的结果）一旦不符就强制重排。
  详见第二节"为什么还会偶发只剩 1/4 屏"。
- **如果你还在用 v1.5 或更早**：遇到时点一下 **「修复画面」** 即可救回；
  升级到 v1.6 后会自动修，不用手动点。

**Q：折叠屏（Galaxy Z Flip 等）的外屏会被误判成外接屏吗？**

`android.view.Display` 没有公开的 `getType()`，无法直接问"这块屏是内置还是外接"。
v1.2 起用两个更硬的信号排除机身自带屏（`DisplayUtil.looksInternal`）：

1. **有挖孔 / 刘海的 `DisplayCutout`** —— 只有机身自带屏才会有，外接屏恒为 `null`
2. **名字与默认屏相同** —— 三星折叠机的内屏和外屏同名（`内置屏幕`）

这比 v1.1 只用 `STATE_ON` 过滤可靠得多：**手机折叠且外屏完全点亮**时，
v1.1 会把外屏列出来并去旋转它，而旋转一块机身显示屏会连带搅乱整机显示几何 ——
正是上面"画面错位"的高危诱因之一。

**Q：并发模式下封面屏亮了但一片黑，什么都点不了** ⭐

那是**系统自己的锅**：`state 4` 只是把封面屏点亮，上面挂的是系统那个空跑的
`SubHomeActivity`（三星封面屏界面在"非折叠"姿态下不渲染内容），所以看着是黑的。

v1.8 起点「双屏」页的 **在封面屏打开副屏桌面**（或**一键：内外屏并发 + 封面屏副屏桌面**），
就会往那块屏投一张自带时钟、电量、应用图标的桌面，点图标就能在那块屏上开应用。
用完点 **让封面屏回到系统桌面** 交还给系统。

**Q：怎么让某个应用在封面屏 / 便携屏上打开（像副屏助手那样）？**

v1.9 起不再需要在这里挑应用：点「双屏」页的**启动双屏模式**，外屏上会出现一张
**副屏桌面**（应用图标网格），**在那块屏上点图标就在那块屏打开应用**。
背后执行的是 `am start --display N`，走 Shizuku 的 shell 身份，
**第三方应用也能投**（shell 持有 `START_ANY_ACTIVITY`，未导出的组件同样能启动）。

**Q：鼠标还是只能操作手机内屏，外接屏上点不动？** ⭐

默认外接屏是**镜像**，鼠标事件会被路由到默认屏。要鼠标归外接屏，需要把外接屏
变成**独立桌面** —— 「双屏」页的 **免 DeX 桌面模式** 打开（并**重启**）即可，
这是 AOSP 自带的机制，和 DeX 无关。

先点 **鼠标检测** 看现状：它会把 `dumpsys input` 里的
`Default mouse displayId` / `FocusedDisplayId` 翻译成"手机内屏 / 封面屏 / 外接屏"。
若开了桌面模式鼠标仍停在手机屏，把光标往屏幕边缘推一推，或重插一次鼠标。

> 实测结论：**Android 平台层只给了这一个可靠口子**。系统内部确实有个
> `Overriden mouse displayId`（在 `dumpsys input` 里能看到），但框架里没有把它暴露成
> shell/公开接口（在 `services.jar` 里搜不到 `setMouseDisplayId` 之类的入口），
> 所以"把鼠标钉到某块屏"只能靠桌面模式，不能靠一条命令硬指。
> 封面屏本来就是触控用的，不给鼠标也不影响。

**Q：为什么「封面屏」相关按钮有时会说"没找到目标屏"？**

因为封面屏只有在**内外屏并发**时才算"一块可投的屏"。按钮已经做了自动处理：
拿不到就先切 `state 4`、等 2 秒再投。如果仍然失败，去「内屏管理」页确认折叠状态
是 `展开 OPENED`，再点一次。

**Q：说明书里写的 `am start --display N` 我照着写进清单注释，构建直接报错？**

XML 注释里**不能出现连续两个连字符**（这是 XML 规范）。`Error parsing
AndroidManifest.xml` 就是这个原因，而且它不告诉你行号 —— 把注释里的
`--display` 改成 `display 参数` 就好了。放在属性值或正文里是合法的。

**Q：我用 SecondScreen 改内屏分辨率，现在还要它吗？** ⭐

**v1.3 起这件事本应用也能做了，所以它变成可选。** 如果你本来就习惯 SecondScreen、
不打算卸它，也能共存 —— 但**必须避免两个应用同时自动写显示参数**：

| 方案 | 怎么做 |
|---|---|
| **推荐：只用本应用** | 点一次「授予弹窗权限」→ 点开「内屏分辨率接管」按钮 → 把 SecondScreen 关掉或卸载 |
| **保留 SecondScreen** | 在本应用里把「插入便携屏时弹窗询问」和「自动套用便携屏分辨率」关掉，只在需要时手动点按钮；同时把 **SecondScreen 的自动应用配置关掉**，只留手动 |

> 为什么不能两个都开着自动模式：它们调的是同一套显示几何
> （`setForcedDisplaySize` / `wm size`），同时写会形成竞态 → 画面整体错位（见上一条）。
> 本应用用的是 `wm size`，SecondScreen 用 `WindowManagerService.setForcedDisplaySize`，
> 最终落到同一处。

> 补充一个实测细节：`appops set <包名> SYSTEM_ALERT_WINDOW allow` 只对
> **在清单里声明了 `SYSTEM_ALERT_WINDOW` 权限**的应用生效。v1.3 之前本应用没声明，
> 所以这条命令静默失败（`appops get` 一直显示 `default`）；声明之后就能正常授予了。

**Q：插入便携屏后没看到弹窗**

按顺序查：

1. **手机是不是锁屏/息屏了？** 锁屏时本应用刻意不弹（既看不到还会平白亮屏），
   这种情况走的是通知横幅 —— 下拉通知栏点「启用」即可。
2. **有没有给「显示在其他应用上层」权限？** 没给的话弹窗会被系统拦掉，
   但**一定会有一条高优先级通知横幅**兜底，横幅上直接能点「启用 / 不用」。
   到应用里点「授予弹窗权限」可补上。
3. 想立刻验证链路：点应用里的 **「测试弹窗」**。

**Q：在 App 里开了"锁手机方向（横屏）"，后来用系统下拉快捷开关切回了自动旋转，App 里开关怎么还开着？**

**v1.6 已修**。这两处确实是同一个系统设置的两副面孔：

- App 里打开"锁手机方向"= 写 `Settings.System.ACCELEROMETER_ROTATION = 0` + `USER_ROTATION = 1`
- 系统下拉快捷开关"自动旋转"= 同一条 `ACCELEROMETER_ROTATION`

所以当你从下拉菜单切回自动旋转时，系统把 `ACCELEROMETER_ROTATION` 改回了 1，
而旧版 App 不知道，界面开关还显示"开"、内部也仍按"锁定"处理 —— 指令与实际状态
不一致，也会诱发显示不全。

v1.6 起，**服务和界面都会读这个系统值**（`checkPhoneLockDivergence` /
`syncPhoneLockSwitch`）：只要确认系统已回到自动旋转（**连续 2 次命中、且过了宽限期**，
避免和 App 自己刚写入的值打架），就自动把 App 内开关关掉并给一句提示。
所以你用系统的下拉开关改也没问题，两边会自动对齐。

**Q：会不会影响手机内屏？**

- **旋转**：不会。所有旋转命令都带 `-d <外接屏ID>`，只作用于外接显示屏；
  且 v1.2 起还有上面两道排除，机身屏根本进不了候选列表。
- **分辨率**：会，但这是你要的功能，而且完全可控 —— 它是显式开关 + 弹窗确认的，
  界面上随时能点「还原原生」，退出时也给你还原成面板原生分辨率。

### v2.17（「保存参数设置」补回被误删的两项）

「保存参数设置」表的项数走过 `10（v2.6）→ 6（v2.7 压成一行两项）→ 4（v2.14）`。
其中 10→6 是版式压缩；**4 是 v2.14 改的** —— 当时为了堵"接屏时档案偷改两个总开关"，
把 `sync` / `lockPhone` / `phoneRot` 三个字段连同表格里「方向同步」「自动旋转」两行一起删了。
连带把 v2.8 特意做的「自动旋转」三态（`开` / `横向锁定` / `竖向锁定`）也带走了。

这次把字段和两行都放回来，**表格回到 6 项 3 行**：

```
display N · 面板 1920×1080 · 设置分辨率 1080×1920（已保存）

设置项      已保存    当前        设置项      已保存    当前
方向同步     关       开          自动旋转     开      横向锁定
同步模式   跟随手机  跟随手机     竖屏方向   竖向锁定   竖向锁定
横屏方向   横向锁定  横向锁定     DPI        不改      不改
```

⚠️ **「存」和「套用」是两件事**：
- 这两个开关现在会**存**进档案 —— 表格的「已保存」列因此有了对照值；
- 但 `applyTo()` **仍然不写回**它们，接屏那一刻不会替你改开关。

v2.14 的修法是"把字段删掉"，等于拿删功能去堵乱套用 —— 乱套用确实堵住了，功能也白丢了。
正确做法是**只堵套用那一处**。`exists()` / `load()` 的存在性判据继续用 `land` 键。

### v2.16（折叠切换后保持亮屏 + 更新日志汇总补回）

**① 切到折叠不再黑屏**

「折叠/展开模式切换」切到折叠那一下，屏幕会黑 —— 根因在系统侧：`cmd device_state state 0`
一落地，框架就按**"合盖"**处理，直接 `goToSleep`：

```
+1s  display 0 screenOn=false / display 1 screenOn=false / wakefulness=Dozing    ← 两块屏同时黑
+2s  display 1 screenOn=true（只剩 AOD） / wakefulness=Dozing                    ← 并没有亮回来
```

⚠️ 跟息屏超时无关（用户的超时是"永不"），而且只有**真的发生状态翻转**时才睡。

改法：`toggleFold()` 收尾加了 `keepScreenOn()` —— 目标是折叠态时先等 1100ms 让那一刀落地，
再用 `PowerManager.isInteractive()` 判断，没醒就发 `KEYCODE_WAKEUP`（走 Shizuku），最多补 3 刀。
展开方向本来就不睡，直接看，不添延迟。

实测（同一条界面路径：`uiautomator dump` 找到按钮 → `input tap`）：
v2.15 `+1s…+8s` 全 `Dozing`；v2.16 `+1s Dozing → +2s 起 Awake` 且封面屏亮着，稳到 12 秒以上。

**② 更新日志汇总补回**

v2.9 – v2.15 那七版一直在「外屏小组件 / 两个开关」两处来回，中途的记录当时按用户要求撤掉了；
现在问题定稿，按**汇总**写回（合并成一条），只留结论：

- 锁横与自适应旋转的联动 —— 方向判定不再把「锁手机方向」当输入源；
- 只支持竖屏的应用里的黑边 —— 手机竖屏时外接屏转 270°（与内屏同比例）；
- 外屏小组件从「设置 → 外屏 → 小组件」消失 —— 内屏 / 封面屏拆成两份独立声明；
- 外屏小组件铺满 2×2 —— 折叠/展开 · 方向同步 · 双屏模式 · 锁横屏，按钮自带开关状态；
- 小组件上点「折叠/展开」会连切两次 —— 一次点击只认第一次；
- 接屏时套用的旧档案不再改「方向同步 / 锁横」两个开关。

### v2.13（方向判定跟「锁手机方向」真正解耦 + 外屏面板把 2×2 铺满）

**① 锁着的时候别再问屏 —— 方向就是锁定角度本身**

v2.12 把 v2.11 那套重力感应撤掉之后，这里仍然没做对。真正的坑在**输入源**：

判"手机是横是竖"这一步去问"真正亮着的那块内置屏"，而**合盖时那块屏是封面屏**
（748×720，天生就是横面板）。封面屏竖握时 `rotation` 是 1/3，按面板原生宽高比一换算，
恰好得到**"竖屏"** → 外接屏被转到 270°。更阴的是封面屏不是默认屏，
与系统旋转策略交叉校验的那段**只对默认屏做**、整段跳过 —— 于是没有任何一步能把它拉回来。
表现出来就是「一开方向同步反而歪了 / 铺不满」。

改法：**判据分两条腿**。

- 锁着 → 方向 = `lockedPortrait()`：拿 `Prefs.getPhoneRotation()` 配**默认屏**的面板原生宽高比
  换算（1080×2640 是竖面板 ⇒ 1/3 = 横、0/2 = 竖）。不看任何屏的 state / rotation。
- 没锁 → 才去问"真正亮着的那块内置屏"，并用 `policyRotation()`（`user_rotation`）交叉校验。

一句话：这个开关的语义就是"手机现在被固定在哪个角度"，那外接屏要跟随的方向当然就是那个角度本身。

**② 外屏「双屏快捷面板」铺满 2×2，四格四个按钮**

外屏的格子是 2×2 = 150×133dp，而之前它复用的还是内屏那份布局 —— 一条固定 56dp 高的窄条
居中摆着，上下空出一大截。尺寸动不了（改小会让组件从托盘消失，见 v2.11），那就把这 2×2 **用满**：

- 新布局 `widget_panel_2x2.xml`：根布局直接铺底色铺满，内部 2×2 `layout_weight` 四格；
- 四个按钮 —— 折叠/展开 · 双屏模式 · **方向同步** · **锁横屏**；
- 两个开关式按钮的状态现读 `Prefs` 画上去（名字 + 开/关 两行，开 = 本色 / 关 = 灰底），
  在 App 里改完设置会顺手 `updateAll()` 刷一遍；
- 外屏那份 appwidget 声明（150×133 / targetCell 2×2 / `widgetCategory=keyguard`）**一个字没动**。

内屏那份（2×1 = 110×56dp）保持两个按钮不变。

### v2.12（撤掉重力感应 + 外屏小组件回到 2×2）

撤掉 v2.11 那套重力感应：**手机既然被锁成横向，外接屏就该跟着横着铺满**，按重力转反而
会自己歪回去。同时把外屏小组件声明从 2×1 还原成 2×2（2×1 会让宿主把它踢出托盘）。

> ⚠️ 但这一版**并没有真正修好方向同步** —— 它只是"不再按重力转"，判"手机是横是竖"时
> 依然去读"亮着的那块屏"。见上面 v2.13。

### v2.11（两个开关真正互不干扰 + 外屏小组件试缩到 2×1）

**① 「自动方向同步」和「锁手机方向」一起开时，同步会失效**

「锁手机方向」做的事是关掉系统自动旋转、并把方向钉死在横向 —— 也就是往系统里写
`accelerometer_rotation=0` + `user_rotation=1`。麻烦在于：**同步判"手机现在是横是竖"读的就是这个值**，
钉住之后它永远返回"横屏"，同步便以为手机一直横着放，外接屏自然一动不动 —— 看着就像"同步没生效"。
（单独开锁是好的，因为那时根本不需要判方向。）上一版的"解耦"只做到"各自下发自己的命令"，
没管住这条数据链。

改法：**锁定期间改用重力感应读实际摆放方向**。锁只管手机自己的画面，外接屏照样跟着手走，
两个开关这才真正互不干扰。传感器只在「同步 + 锁」同时开着时才挂，其余时候一律摘掉；
手机平放（重力落在 z 上）时沿用上一次判断，不硬猜。

**② 外屏小组件从 2×2 试缩到 2×1**

先把外屏的格子几何算清楚（从三星自己的尺寸资源反推）：整块外屏是 **4 列 × 4 行**，
列 cell 69dp、行 cell 60.5dp、间距 12dp —— 于是 2×2 = 150×133 ✓、4×2 = 312×133 ✓，
而「2×1」＝ `150×60 dp`。这版就按 `targetCell 2×1` 声明。

> ⚠️ 三星自家在外屏上只用过 133dp 高的槽（2×2 / 4×2 都是 133 高），**没出现过 1 行高的样例** ——
> 宿主认不认这件事还没被证实。这次先按 2×1 声明去试，若被顶回 2 行，外屏上就仍是 2×2。

### v2.10（外屏小组件拆成独立的两个）

v2.9 装上去之后，外屏托盘里**依然找不到**「自适应屏幕」。这轮把同类**活样本**（三星自己的封面屏组件）
的声明逐项拉出来比对，才看清根因：**内外屏被混在同一个组件里**。

三星的做法是**内外屏各一个组件** —— 外屏那个只声明 `widgetCategory="keyguard"`，内屏那个只声明
`home_screen`。我们一直写成 `home_screen|keyguard`（两个位都占），外屏托盘就不认它。实测活样本：

| 组件 | min | resizeMode | widgetCategory |
|---|---|---|---|
| 天气 `WeatherCoverMultiWidgetSimple` | 150×133 dp | 0 | 2 |
| 时钟 `AlarmMultiCoverWidgetProvider2X2` | 150×133 dp | 0 | 8192 |

现在拆成两份：

- **「双屏快捷面板」**（内屏）：`110×56 dp` = 2×1，`widgetCategory=home_screen`；
- **「双屏快捷面板（外屏）」**（封面屏，新增）：`150×133 dp` = **2×2**，`widgetCategory=keyguard`、
  `resizeMode=none`，声明与天气那份逐项一致。

> ⚠️ 外屏那份的实例 adb 造不出来（系统 pin 框只投内屏），**要你在外屏上手动重新钉一次**才能看到它。

### v2.9（外屏小组件试按 2×2 摆 —— 该做法有误，已被 v2.10 取代）

按「阿田自用」那份 2×2 配置照抄了一遍（150×133 + `targetCell 2×2` + 三星私有 `widgetSize`/`widgetStyle`），
结果组件**从托盘里消失**。事后查清：那份 XML 是**废弃资源**，没有任何 receiver 引用它
（它 manifest 里唯一的 provider 引用的是 352×339 / 4×4，所以它在外屏上始终是整页）。**这条路作废**。

### v2.8（折叠切换不再要点两次 + 「自动旋转」三态 + 封面屏小组件真的变小）

用户拿去用之后回来说了三件事，都是"看着改了、用起来没变"。

**① 「折叠/展开模式切换」还是要点两次**

按用户给的复现路径（**先用别的软件改折叠模式的外屏显示** → 插便携屏 → 进本应用点切换），
第一次点击毫无反应，必须再点一次。

根因在判据读错了源。`cmd device_state` 其实有**三个**值：

```
Committed state: identifier=1, name='TENT'     ← 覆盖后正在生效的（print-state 给的就是它）
Base state:      identifier=0, name='CLOSED'   ← 传感器说的物理状态
Override state:  identifier=1, name='TENT'
```

`cmd device_state print-state` 只给 **Committed**，也就是"**有覆盖就是覆盖值**"。
别的软件把 override 设成 `TENT` 之后，盖子明明合着、读回来却是"帐篷"—— 旧判断是
"不是 `CLOSED` 就算展开"，于是它认为当前是展开态、下发了"切到折叠"，而用户眼前本来就是折叠的外屏
→ 画面毫无变化 → 得再点一次。

现在改成**看哪块屏亮着**：内屏亮 = 展开；内屏灭、封面屏亮 = 折叠；两块都不亮才退回状态机判断
（息屏时内屏同样是灭的，这一级不能省）。顺带把"帐篷 / Flex 半开"也算进折叠态 ——
它们同样只有外屏在显示。下发之后仍然保留上一版的**回读校验**，但判据从"读回来的数字对不对"
改成"**屏态有没有真的翻过去**"—— 数字本来就可能被覆盖污染，拿它当标准等于白校验。

第一个选项卡里那个折叠状态块现在一次报三个值：`当前生效` / `折叠传感器` / `画面在哪块屏`，
被别的软件改过时一眼能看出谁在说谎。

**② 参数表里「自动旋转」那一格显示反了**

那个开关的语义是"**关闭**手机自动旋转并锁定方向"，所以"**开**"应该对应**没锁**的状态。
原来写成了 `锁着 ? "开" : "关"`，正好颠倒。

现在按用户要求做成**三态**：`开`（没锁）/ `横向锁定` / `竖向锁定`。
⚠️ 这里有个容易埋雷的地方：「自动旋转」说的是**手机**自己的方向，手机锁 90°/270° 就是**横向**；
而同一张表里「竖屏方向 / 横屏方向」说的是**外接屏**（便携屏面板天生横放，转 90° 画面才变竖）——
两者刚好相反。所以这一格不能复用给外接屏算角度的那个函数，得单独按手机的约定算。
当前界面只能锁横向，所以平时看到的是 `开` 或 `横向锁定`。

**③ 封面屏小组件：光缩图标没用，格子数才是重点**

上一版只把内容缩了（不再铺满整页），但**占的格子仍是 4×4** —— 封面屏一页就那么点地方，
用户要的是像别的应用那样 **2×2**。

根因是清单里 `widgetCategory` 多带了一个 `keyguard` 位。封面屏宿主对它的处理是：
**带 keyguard 位 = 按"锁屏整页面板"渲染**，不管 `minWidth/minHeight` 声明多少，一律铺满整块封面屏；
**只声明 `home_screen` = 按格子摆放的普通组件**，宿主给出 `150×133 dp` 一格，正好 2×2。

证据是把封面屏宿主（`semHostType=4`）下的实例全 dump 出来比对：

| 组件 | widgetCategory | 封面屏上占几格 |
|---|---|---|
| 本应用（改前）/「阿田自用」 | 含 `keyguard`(2) | 整页（352×339 dp） |
| 天气 / 设备维护 / 例行程序 | 仅 `home_screen`(1) | **2×2**（150×133 dp） |

那个 `keyguard` 位是上一版为了"让它出现在外屏小组件托盘里"顺手加的，其实**托盘那道门是三星私有的
`samsung-appwidget-provider` 声明**在管（见 v2.5），这个位只会帮倒忙。现在 `widgetCategory`
只写 `home_screen`，托盘照常出现，格子数变成 2×2。

> ⚠️ 封面屏上的小组件实例**没法用 adb 生成**（`requestPinAppWidget` 只投内屏），
> 所以这一条要**你自己在封面屏上重新钉一次**才能看到变小。

`versionCode 18 → 19`，`versionName 2.7 → 2.8`。

### v2.5（锁手机方向独立开关 + 按外接屏保存设置 + 修封面屏小组件）

**① 「关闭手机自动旋转，锁定横向」不再是「方向同步」的附庸**

原来这个开关**必须先打开「自适应屏幕（启用自动方向同步）」才会生效** —— 因为写
`Settings.System.ACCELEROMETER_ROTATION` 的动作挂在方向同步服务里，服务不常驻就没人执行。
但"只想把手机钉在横屏、不想让 App 去管外接屏"是完全合理的用法（何况锁横屏本来就用不着
外接屏）。这一版把两个开关彻底解耦：锁定横向**独立生效**。

- `Prefs.shouldKeepRunning()` 增加 `isLockPhoneRotation()` 条件 —— 锁方向开着也让服务常驻；
- 新增 `ACTION_LOCK_PHONE` 与 `RotationService.lockPhoneNow()`，开这个开关直接拉起服务执行，
  不再看「方向同步」的脸色；
- 反过来，**关「方向同步」时如果「锁横向」还开着，不再顺手还原手机的自动旋转** ——
  否则关一个开关会顺带把另一个开关的效果清掉；
- 界面上那句说明也去掉了"同时"二字（它暗示两者耦合），改成 `关闭手机自动旋转，锁定横向`。

> **真机三向实测**：①「方向同步」关着，单独开「锁横向」→ `accelerometer_rotation=0`、
> `user_rotation=1`，服务在跑、日志出 `phone rotation locked to 1`；
> ②再点关 → 自动旋转还原成 1；③开锁横向 → 开方向同步 → 关方向同步 →
> 自动旋转**仍是 0**（锁没被误清），`enabled=false / lock_phone_rotation=true`。

**② 新增「按外接屏保存设置」（按屏记配置）**

**③ 修掉：封面屏（外屏）的「小组件」列表里看不到本应用**

之前一直按 AOSP 的思路调 `widgetCategory`（`home_screen` / `keyguard` / `0x2000`），
**全都没用** —— 把全机 193 个 provider 数了一遍，发现出现在封面屏托盘里的应用（阿田自用、

<samsung-appwidget-provider display="sub_screen" />

### v2.2（修并发模式下外接屏锁 270° + 两个小组件合并成「双屏快捷面板」）

  `RotationService` 对**默认屏**做交叉校验，**屏上读数与系统策略矛盾时采信策略**。
  只对默认屏做（封面屏不受 `user_rotation` 驱动）。

### v2.0（修"横屏却被转 270°" + 每次转方向都误重排 + 首个选项卡加三个快捷操作）

**三个真 bug（都是实测定位、非猜测）**

  有历史读数则沿用。详细分析见第二节。
- 🐞 **手机每转一次方向都会多一次 `free → lock` 重排** —— v1.6 的几何校验跑得太早：

  "几何坏了"，于是 `free` 一下再锁回，**free 那一瞬外接屏会跟着系统自己重算方向，
  看起来就是当场乱转**。改为**只有角度已落在目标上时才做几何校验**（能力不减，误报全消）。
- 🐞 **关掉「自适应旋转」后手机被永久钉在横屏** —— 还原手机自动旋转的代码只在

### v1.6（改名 + 多选项卡 + 弹窗自适应 + 根治偶发 1/4 屏 + 开关同步）
- ✅ **App 改名**：「外接屏方向管家」→ **「便携屏中心」**（`app_name`）。
  通知渠道名也从"屏幕方向同步 / 接入询问"改为"便携屏方向同步 / 便携屏接入询问"。
- 🐞 **根治偶发"只显示 1/4 屏"**。根因是旧逻辑只校验外接屏的 `rotation` 角度，
  **不校验显示几何**；插屏 / 折叠展开会让系统重算几何但 `rotation` 数值不变，
  于是被误判成"已在位"而跳过下发，半成品几何就留在屏幕上（见第二节）。
  修法：新增**拓扑签名**（内屏 on/off + 内屏面板尺寸 + 外接屏集合）识别插拔/折叠事件，
  配合**几何校验**（`getRealSize()` 是否等于面板原尺寸按目标角度转置的结果），
  一旦不符就强制 `free → lock` 重排。
- 🪟 **弹窗按窗口等比缩放**。改成 `ScrollView` 可滚动主体 + **固定底部按钮栏**，
  再以真实测量的内容高度对窗口高度做反馈循环（`settle()`）：先按最大倍率试排，
  放不下就交替"长大窗口 / 缩小字号"，直到完整放下。横屏、任意 DPI 下按钮都可见可点。
- 🗂 **主界面重构成三个选项卡**（此前一长条太臃肿）：
  **① 自动旋转**（同步开关、锁手机方向、同步模式、角度、手动校准、修复画面、日志）、
  **② 内屏分辨率**（接管开关、分辨率/DPI、自动套用、接管时机、应用/还原、弹窗权限）、
  **③ 授权与状态**（Shizuku 授权、实时状态、说明）。
  选项卡用 `RadioGroup` 实现（不依赖 AndroidX），选中态绿底、记忆上次所在选项卡。
- 🔁 **修复开关不同步**：在 App 内打开了"锁手机方向（横屏）"后，用系统下拉快捷开关
  手动切回"自动旋转"，App 里的开关不会跟着关 —— 这也会诱发显示不全。
  现在服务（`checkPhoneLockDivergence`）与界面（`syncPhoneLockSwitch`）都会读
  `Settings.System.ACCELEROMETER_ROTATION`，确认系统已回到自动旋转（连续 2 次命中、
  过了宽限期）后，自动把 App 内开关关掉并提示。
- 🎨 细节：移除重复标题栏（应用主题改 `Theme.DeviceDefault.Light.NoActionBar`）、
  "打开 Shizuku" 按钮不再被系统强制大写（`textAllCaps=false`）。
- 版本号升至 `1.6` / `versionCode 7`

### v1.5（修响应慢：切换从 2.6~3.3 秒降到 0.44 秒）
- 🚀 **响应速度提升约 6 倍**。真机实测：转竖屏 2.59 s → **0.44 s**，
  转横屏 3.32 s → **0.45 s**，1.2 秒内快速回切也从"被压住"变成 **0.44 s**。
- 🔍 **根因不是命令慢**：`wm` 单次只要 0.02 秒。慢在决策 —— 旧逻辑只在
  每 2 秒一次的轮询里检查手机方向，"发现变化"和"稳定够了"这两步都被量化成
  一个完整的轮询周期，于是 2~4 秒。
- 🔧 `onDisplayChanged` **只认 display 0**（手机内屏）：一变化立刻评估。
  外接屏的变化是自己命令的回声，忽略掉，不会像早期版本那样自激刷命令。
- 🔧 方向稳定判定改成**「预约一次评估」**：方向一变就排一个 `STABLE_MS+30ms`
  之后的评估，不再靠下一次轮询去碰运气。
- 🔧 `STABLE_MS` 900 → 400 ms（系统本身已对重力感应去抖）；
  兜底轮询 2000 → 1500 ms。
- 🔧 静默期支持**提前解除**：判据改成"上一刀是否已确认落地"（当前角度＝上次的目标
  角度），而不是死等满 2.5 秒。既保住了"不在事务提交中补刀"的防错位保护，
  又不再让手机来回翻转白等。
- 🔧 `evalRunnable` 与 `pollRunnable` 拆成两个 Runnable —— 共用会在 Handler 上
  挂出两条自续链，`removeCallbacks` 撤不干净，评估次数会翻倍。
- 版本号升至 `1.5` / `versionCode 6`

### v1.4（按钮开关 + 自动识别便携屏分辨率 + 横屏自动转竖屏）

  外接屏信息也补上了「原生 1920×1080 · 当前 1080×1920 · 建议内屏分辨率」。

## 七、自己重新编译

环境：**JDK 17**、**Android SDK**（platform 34 + build-tools 34.0.0）、**Gradle 8.11.1**

```powershell
# 换成你自己的路径
$env:JAVA_HOME    = "C:\Program Files\Java\jdk-17"
$env:ANDROID_HOME = "D:\Android\sdk"

gradle -p . assembleDebug
```

产物：`app/build/outputs/apk/debug/app-debug.apk`

> 没有装 Gradle 的话，也可以直接用 Android Studio 打开本目录编译（
> `local.properties` 里写一行 `sdk.dir=<你的 SDK 路径>` 即可）。

> Shizuku 客户端库来自 Maven Central（`dev.rikka.shizuku:api` / `:provider`），
> 如果构建时拉不动依赖，可在 `settings.gradle` 里把 `mavenCentral()` 换成
> `https://maven.aliyun.com/repository/public`。
